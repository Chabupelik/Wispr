# 🚀 Wispr — Isolated Browser & Secure Tunneling Platform

**Wispr** — это клиент-серверная платформа с гибридной архитектурой, разработанная для обеспечения максимальной изоляции веб-сессий, безопасного туннелирования трафика и централизованного управления клиентами.

Ключевая особенность проекта — использование изолированных in-memory профилей на базе Microsoft Edge WebView2, трафик которых жестко маршрутизируется через защищенный WebSocket-туннель (WISP) с привязкой к аппаратному идентификатору устройства (HWID). Платформа также включает встроенный режим маскировки (Decoy), систему предотвращения утечек и инструменты удаленного мониторинга.

---

## 🎯 1. Архитектура и концепция

Платформа решает задачи безопасной работы в сетях с недоверенной инфраструктурой или строгими политиками фильтрации:

1. **Безопасное туннелирование:** Весь трафик браузера прозрачно инкапсулируется в зашифрованный WebSocket-канал (WISP). Для систем DPI и сетевого оборудования обмен выглядит как стандартное HTTPS-соединение с доверенным веб-сервисом.
2. **Изоляция браузерных профилей:** В отличие от обычных браузеров, клиент использует эфемерные WebView2-сессии, гарантируя полное отсутствие утечек состояния между сессиями (cookie, кэш, local storage).
3. **Fail-safe Networking & Скрытый режим (Decoy):** Платформа имеет встроенный резервный механизм — «дежурный браузер», позволяющий осуществлять обычный веб-серфинг. Переход в режим защищенного туннелирования активируется только после авторизации, что защищает систему от несанкционированного доступа.

## 🏗 2. Архитектура и сетевой стек

Архитектура проекта разделена на два независимых контура: **Desktop Client (Rust / Tauri v2 + Vue 3)** и **Remote Backend (Node.js / Fastify)**.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Desktop Client (Wispr)                          │
│     WebView2 (In-Memory)  │  Local Loopback Proxy (Rust / Tokio)       │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Wisp over WebSocket (TLS + AES-GCM)
┌───────────────────────────────────▼────────────────────────────────────┐
│                        Wispr Server (Linux VPS)                        │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │ Fastify Wisp Gateway: распаковка TCP/UDP, выполнение запросов    │  │
│  ├──────────────────────────────────────────────────────────────────┤  │
│  │ SSE Management: удаленное управление сессиями и клиентами        │  │
│  └────────────────────────────────┬─────────────────────────────────┘  │
└───────────────────┬───────────────┴─────────────────┬──────────────────┘
                    │                                 │
┌───────────────────▼───────────┐         ┌───────────▼──────────────────┐
│          PostgreSQL           │         │            Redis             │
│    Сессии, логи, события      │         │     OTP, Single-Session      │
└───────────────────────────────┘         └──────────────────────────────┘
                    ▲
                    │ aiogram 3.x
┌───────────────────┴───────────┐
│     Telegram Admin Bot        │
│  OTP, мониторинг, Whitelist   │
└───────────────────────────────┘
```

### Схема прохождения трафика
`Desktop Client` ➔ `Local Loopback Proxy (Rust)` ➔ `Wisp over WebSocket (TLS)` ➔ `VPS Server (Node.js)` ➔ `Target Website`

1. **Local Loopback (Rust / Tokio):** Встроенный в браузер локальный прокси-сервер перехватывает сетевые запросы движка WebView2.
2. **Wisp Tunneling:** Локальный прокси упаковывает сырые TCP/UDP пакеты в протокол Wisp и отправляет их через зашифрованный WebSocket-канал на бэкенд.
3. **Remote Execution:** VPS-сервер распаковывает Wisp-фреймы и выполняет запросы от своего внешнего IP-адреса, возвращая результат клиенту.

### Предотвращение сетевых утечек
- **WebRTC & DNS:** Полностью блокируются утечки реального IP-адреса. DNS-резолвинг происходит строго на стороне VPS.
- **QUIC / HTTP3:** Принудительно отключается для исключения UDP-утечек в обход туннеля.
- **Killswitch:** При разрыве Wisp-туннеля локальный Loopback-прокси немедленно сбрасывает все соединения, исключая возможность выхода в сеть с реального IP.

### Load Balancing & Отказоустойчивость
Бэкенд динамически распределяет WISP-сессии по пулу endpoint'ов (`stream.*`, `assets.*`, `edge.*`) для равномерного распределения сетевой нагрузки и повышения отказоустойчивости инфраструктуры.

## 🕵️‍♂️ 3. Изоляция сессий и управление состоянием

### Жизненный цикл эфемерных сессий
- **Нулевой контекст:** При переключении в туннелируемый режим запускается полностью изолированная сессия WebView2 (In-Memory / InPrivate).
- **Stateless Cleanup:** Rust-ядро выполняет агрессивную очистку кэша, локального профиля (`com.google.chrome`) и временных файлов при любом переходе между режимами или закрытии приложения.

### Управление цифровым отпечатком (Fingerprint Management)
- **Нормализация заголовков:** Браузер переопределяет Client Hints (`Sec-Ch-Ua`, `Sec-Ch-Ua-Mobile`) и подменяет свойства объекта `navigator` через инъекцию JavaScript на этапе `DocumentCreated` для стандартизации отпечатка браузера.
- Флаг `--disable-blink-features=AutomationControlled` отключает стандартные индикаторы автоматизации WebView.

## 🛡 4. Безопасность и контроль доступа

### Защита WISP-туннеля (Payload Encryption & Handshake)
- **AES-GCM Encryption:** Трафик внутри WebSocket-туннеля WISP дополнительно шифруется на уровне приложения с помощью **AES-256-GCM** (поверх стандартного TLS).
- **HMAC-подпись и защита в глубину (Defense-in-Depth):** Каждый запрос на создание туннеля подписывается алгоритмом `SHA256(JWT + Timestamp + Obfuscated_Salt)`. Секретная соль обфусцируется на этапе компиляции Rust-клиента через макрос `obfstr`, а сервер проверяет валидность временной метки (`Anti-Replay`, окно 1 час) и JWT-токена.
- **Защита от Timing Attacks:** Проверка криптографических подписей на сервере выполняется за константное время через `crypto.timingSafeEqual`.

### Device-Bound Authentication
- Сервер генерирует токен с привязкой к уникальному аппаратному идентификатору (HWID) устройства.
- В JWT записывается односторонний хэш устройства: `HMAC-SHA256(deviceId, JWT_SECRET)`.
- **Single-Session Enforcement:** Redis отслеживает активный HWID для каждой учетной записи. При авторизации с другого устройства предыдущая сессия деавторизуется, а её WISP-сокеты немедленно обрываются.

### Централизованное управление клиентами (Remote Control)
Через защищенное Server-Sent Events (SSE) соединение администратор сервера может удаленно управлять активными клиентами:
- **Remote Termination (`del`):** Удаленное принудительное завершение процесса клиента и сброс его локального состояния.
- **Session Revocation (`norm`):** Принудительный сброс активной сессии пользователя.
- **Self-Destruction:** Удаленный вызов деинсталляции и полного удаления приложения с устройства.
- **Find Device:** Механизм визуальной идентификации активных клиентов с помощью скрытых виджетов.

### Административная панель (Telegram Bot)
- **Белые списки:** Поддержка Whitelist для IP-адресов серверов и Telegram-аккаунтов, имеющих право генерировать OTP-коды.
- **Аудит и история:** Централизованный сбор логов входов/выходов (Device Events) и посещенных ресурсов в БД без сохранения на клиенте.
- **Статистика трафика:** Учет объема переданных данных WISP-сессий в реальном времени.

## 💻 5. Стек технологий

| Слой | Технологии |
|---|---|
| **Core & Tunneling** | Rust, Tauri v2, Tokio, Tungstenite (WebSocket), Byteorder |
| **Web Engine** | Microsoft Edge WebView2 (InPrivate / In-Memory Mode) |
| **Frontend (UI)** | Vue 3, Vite, Pinia, Tailwind CSS / Vanilla CSS |
| **Backend Gateway** | Node.js, Fastify, Wisp-JS, SSE (Server-Sent Events) |
| **Базы данных и кэш** | PostgreSQL (пользователи, история сессий и события), Redis (OTP, Single-Session Lock) |
| **Боты и автоматизация** | Python 3.12, aiogram 3.x, aiohttp |
| **Инфраструктура** | Linux VPS, Docker, Docker Compose, Nginx |

## ⚙️ 6. Запуск и сборка

### Предварительные требования
- **Для клиента:** Windows 10/11, Rust Toolchain, Node.js 18+, WebView2 Runtime.
- **Для сервера:** Linux VPS, Docker & Docker Compose, Node.js 18+.

### Настройка окружения
1. Скопируйте шаблон конфигурации бэкенда:
   ```bash
   cp backend/.env.example backend/.env
   # Укажите DATABASE_URL, REDIS_URL, JWT_SECRET, BOT_TOKEN и WISP_SALT
   ```
2. Скопируйте шаблон конфигурации фронтенда:
   ```bash
   cp frontend/.env.example frontend/.env
   # Укажите VITE_API_DOMAIN и WISP_SALT (значение должно совпадать с бэкендом)
   ```

### Запуск в режиме разработки (Dev)
```bash
# Бэкенд
cd backend
npm install
npm start

# Фронтенд (десктопный клиент)
cd frontend
npm install
npm run tauri dev
```

### Релизная сборка (Production)
Сборка изолированного бинарника клиента:
```bash
cd frontend
npm run tauri build
```
Готовый `.exe` файл будет сформирован в директории `frontend/src-tauri/target/release/`.
